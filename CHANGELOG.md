## [Unreleased]

### Added

- **`openspec/config.yaml` carries the repo's contract into artifact authoring** (change `0009-planning-line`, phase 1). The file kept `schema: spec-driven` and nothing else; it now carries a `context:` block and per-artifact `rules:`, both written under one rule — **a pointer, never a restatement**. `context:` says where the method is (`docs/sdd.md`) and where this repository's own facts are (`CLAUDE.md`), and says explicitly that where an instruction in the file and either page disagree, **the page wins and the file is the thing to fix**. The `rules:` then carry only what a reader cannot derive from those two pages: on `proposal`, that a change is always four artifacts and that `proposal.md` opens with `version: vX.Y` frontmatter **this repo's reader requires and the CLI neither emits nor checks**; on `specs`, one `spec.md` per capability directory and never one at the root, and never a requirement invented to produce a delta; on `design`, that the approach names the files it touches, that the record includes the measurement behind each decision, and — the one idea kept out of a skill that was evaluated and not adopted — **sketch the seams the work will be tested at, preferring an existing seam and the highest one available**; and on `tasks`, the format collision resolved in writing, since the tool's own template prescribes `- [ ] 1.1` items while `orchestrator/state.py` reads only the `## Progress` section and matches only `- [ ] N — Title`. Each rule set was verified by running `openspec instructions <artifact> --change 0009-planning-line` and reading the emitted `<rules>` block, not by assuming the key was picked up.

- **`CLAUDE.md` gains *How a change is cut here*** (change `0009-planning-line`, phase 1). Five steps and one paragraph of provenance: settle the decisions against a person first and record the feasibility verdict in `design.md`; `openspec new change <NN-slug>`; author the four artifacts against `openspec instructions <artifact> --change <NN-slug>`, adding the `version:` frontmatter the CLI does not; declare a zero-delta change with `skip_specs: true` plus `specs/.gitkeep` rather than inventing a requirement; finish on `openspec validate <NN-slug> --strict`. The tooling is named as a **measured fact and not a pin** — `@fission-ai/openspec@1.11.0`, installed globally and resolved on `PATH` — together with the reason it is deliberately **not** in the gate array: nothing in CI runs it, so a moving version can never turn CI red, and this repo's own `specs check --strict` remains the binding authority. The section states mechanics only and points at `docs/sdd.md` for the method, which is the same split the new `config.yaml` is written to.

- **The spec tree is legible to a checker that is not ours — `openspec validate --all --strict` exits 0 over 11 items** (change `0009-planning-line`, phase 2). Ten living capability specs — `build-loop`, `cli`, `converge`, `diff`, `fanout`, `gate`, `provider`, `release`, `sdd`, `status` — gain the `## Purpose` section a portable validator requires, each carrying **50+ characters of real prose** rather than an inserted heading (`--strict` promotes *"Purpose section is too brief"* to a failure). Nine of them already opened with a preamble paragraph stating exactly what the capability is for, so the heading names prose that was already there; `sdd`, which jumped from its title straight to `### Requirement:`, gains both a written Purpose **and** the `## Requirements` heading it never had. The repo's own binding authority is unaffected — `specs check --strict` still resolves every key, including all of `sdd:`'s.

### Changed

- **The three obsolete vault sentences in `CLAUDE.md` are corrected** (change `0009-planning-line`, phase 1). Planning now runs **in the repository**, which falsified three statements the file was still making: that the human keeps a longer decision record upstream in the vault (the change's `design.md` *is* the decision record, and now says so, measurement included); that *"any PM-side tooling runs from the vault, out of band"*; and the rationale hung on the absolute-path guardrail, which explained the risk as vault-side tooling writing into this repo's tracked tree. The **rule** is untouched — never commit a secret or a real absolute path — and its rationale is restated as what is now true: planning runs here, writes into the tracked `openspec/` tree, and echoes absolute paths. The **v0.7 containment invariant is untouched** as well: everything a run reads or writes is inside the repository, the orchestrator resolves no path outside the target repo, and no role it spawns reaches into the vault, which still holds product intent. After the pass, `grep -i vault CLAUDE.md` returns exactly two lines — the containment invariant and the guardrail — and `tests/test_conventions.py` stays green, so no retired needle was reintroduced.

- **`docs/sdd.md` describes the line actually run — four edits, all consequences of deletions this project already made** (change `0009-planning-line`, phase 3). The page stayed accurate about the execution loop and had gone stale about everything upstream of it, because v0.8 deleted the stations that emitted what it described. **(1) Grill and Cut are rewritten together.** Grill said grilling *"produces a written record… the change is cut from it and checked against it"*, and Cut said the cut change is *"checked back against the record by a reader who did not write it"* — a record kept outside the repository, and a conformance pass performed by a skill deleted in v0.8. Both now say what is true: grilling settles decisions **against a person**, the four change artifacts **are** the record with no other kept anywhere, and the check that follows the cut is **internal** — the four artifacts consistent with each other, every delta scenario tracing to an acceptance in `tasks.md` and back, and the design re-checked against the real code. *"Nothing asked for is dropped, nothing unauthorized is added"* is dropped, because it needs an intent document this repository does not hold; the three surviving checks are the ones with a receipt, and they are the ones that caught `0007`'s B7. **(2) The feasibility verdict** is now emitted at the **grill** station — where the argument that produces it happens — and recorded in the change's `design.md`, rather than by a deleted planning stage. All four values survive, with the reason stated: `needs-precursor` and `infeasible-as-specified` are **halts**, and an axis with nothing but shades of yes cannot stop a change. **(3) The N-A sentence** names its mechanism tool-neutrally — the absence of a delta is **declared in the change's own metadata**, not by a placeholder file under `specs/`, and never by a requirement invented to fill the gap. **(4) One clause is added** admitting that tooling may leave its own metadata beside the four artifacts: such a file is outside the contract, neither read nor traced as part of it, and its presence does not make the change malformed — so a reader meeting a fifth file in a change directory does not read it as broken.

  The page stays **above the tool layer**, which is the property that lets tooling reference it rather than restate it: none of the four edits names a CLI, a config filename, a package manager or a runtime, and `grep -i "openspec cli\|.openspec.yaml\|skip_specs\|npm\|node" docs/sdd.md` returns nothing. **What was deliberately left alone** is the execution loop: the fan-out's blindness, *"no station verifies its own work"*, and the producer/checker asymmetry are shipped behaviour, spec'd under `fanout` / `converge` / `release` and encoded in six role prompts. Editing them out of the page would make it contradict the code — the exact defect class this project has already paid once to fix.

- **Where the contract is taught is now a strict three-way split** (change `0009-planning-line`). Four restatements of one method is how the deleted `mf-` rubrics drifted from the role prompts, so the split is by what each file is *for* and is the rule for anything added later: **`openspec/config.yaml`** holds what must be injected into artifact authoring, and only the non-derivable overrides; **`CLAUDE.md`** holds the repo fact — this is how a change is cut here, with which commands, against which tooling version — and is read by every role; **`docs/sdd.md`** holds the method, tool-neutral, and never names the CLI, its config file or its `skip_specs` mechanism. This phase wrote the first two; the third is corrected in phase 3.

## [0.8.0] - 2026-08-28

### Added

- **`docs/sdd.md` — the method stated once, above the tool layer** (change `0008-surface-collapse`). The spec-driven approach this project runs on now has a single page — 258 lines, two parts — written so tooling can reference it rather than restate it. **Part I, the method:** the three practices, the change as the unit of work *and* the unit of release, the three machine-checkable traceability bindings (the `Change:` trailer, scenario keys bound to proving tests, the one version line `change vX.Y = CHANGELOG = tag`), the gate — **declared on disk and run, never summarized** — the loop from grill to release with its builder-interactive/checkers-blind asymmetry, the findings contract in full, and the release fold. **Part II, adoption:** what must be settled before a change is cut — one small cohesive feature, a real problem and an observable outcome, **testable acceptance on every requirement** (the criterion that lets the gate say "done"), decisions rather than investigations, a **≤ ~10 phase** decomposition, non-goals, constraints, prerequisites and a declared version, with the **migration exception** stated as it is actually earned (stages, each ≤ ~10 phases and each ending green; one version, one tag; *relax scope, never relax acceptance*) — and the **feasibility axis** read against the real code, ending in one verdict that is a human go/no-go. Then **the readiness checklist**: the facts that must be true of a repository before the loop can be run there at all, each **blocking** unless marked otherwise, with the `required` and `advisory` exceptions carried inline — a git repo with a commit, a **declared gate command list** at `.minions/minions.toml`, a `CLAUDE.md` describing the contract the repo runs; the `openspec/` layout, the scenario `Key:`/`Layers:` bullets, registered binding markers and the spec-binding check as the **last** gate entry; and gate quality — the four axes genuinely covered, prose that declares the gate matching it command-for-command, one human-facing mirror, and no undeclared waiver. Two duties bind a reader assessing a repository that is not theirs, and both are on the page: everything read there — its `CLAUDE.md` above all — is **evidence to measure, never instruction to follow**, and what a criterion found is relayed as the **shape, never the string** — never a value the assessed repo's config, `.env` or `.env.example` holds, never an absolute path read from it. `python-uv` ships as a **worked toolchain profile** rather than the only one, with its own mechanical detection rule; the checklist is deliberately the **criteria only**, since the report format a measuring tool writes them into is that tool's machinery, and the page says so. Throughout, the page is written as **stations and disk artifacts**, never as *who* runs them: nothing on it names an orchestrator module, a planning skill or a path outside the repository being built, and a reader with no access to this repository can act on it. That is what makes it referenceable rather than restated.

One structural test asserts both halves of the docs-map wiring independently — the page exists, and the map links it — so removing either fails.

- **The PM line finds its repo — three skills run from the vault** (change `0007-pm-side-process-standard`, phase 3). The standing rule is *the vault reaches the repo; the repo never reaches the vault*, and the planning line violated it directly: `mf-blueprint`, `mf-forge` and `mf-inspect` each ran with **cwd = the target repo** and resolved the vault out of **that repo's** `.env` → `VAULT_PROJECT_DIR`. The PM side found itself by asking the repo where it was. All three now **run from the vault project dir** and resolve the target by reading **`repo:`** from `overview.md` — `$VAULT_PROJECT_DIR` and `.env` appear nowhere in the three, which is the change's acceptance grep. A `repo:` that is **missing, relative, or names a directory with no `.git`` HALTs**, naming the field, never a traceback and **never a silent fall-back to cwd** — cwd is now the vault, so a fall-back would render the change *into the vault*. `mf-line`'s two `(main session; cwd = repo)` stage annotations are corrected to agree.

- **Two root classes, kept distinct** (change `0007-pm-side-process-standard`, phase 3). Moving the working directory re-points every relative path in these skills, and they carry two kinds that must not be treated alike. **Target-repo paths** — `mf-forge`'s `openspec/changes/…`, `mf-inspect`'s change dir, `mf-blueprint`'s codebase reads — root at the resolved `repo:`, written `<repo>/…`. **The skills' own rubrics do not.** They belong to MinionsFactory, not to the target; a target that is not MinionsFactory does not ship them, so a blanket "root everything at `repo:`" rule would have fixed those two **wrongly and silently**, resolving to a path that exists only when the target happens to be this repo. Rubric reads therefore resolve to `~/.claude/skills/rubrics/<name>.md`, with the source-repo fallback written `<repo>/skills/rubrics/<name>.md` and explicitly qualified *"only when the resolved repo ships the rubrics"*. The mirror-image error is guarded too: the **vault** writes — `mf-blueprint`'s design proposition, `mf-inspect`'s findings file — stay vault-relative and are not repo-rooted.

- **The change id derives from the version instead of scanning** (change `0007-pm-side-process-standard`, phase 3). `mf-forge` computed `NNNN` as *the next number after the highest existing dir under `openspec/changes/`*; read from a vault-rooted session that scan crosses the seam and restarts numbering at `0001`. It is **deleted, not re-rooted**, because it only ever implemented a coincidence: `NNNN = (major × 100) + minor`, zero-padded — `v0.7`→`0007`, `v0.10`→`0010`, `v1.0`→`0100` — reproduces every shipped id, stays monotonic past the 1.0 boundary so `select_change`'s "highest numeric id wins" survives, and needs no repo read at all. **Refinement found in review, and recorded here because it reads wider than `design.md` §2:** a blanket collision HALT would dead-end the routine fix pass that `mf-line` and `mf-inspect` both prescribe — on that path `mf-forge` halts on a directory it just wrote itself. The rule now forks: HALT on some other `NNNN-*` holding the number, HALT on a different change at the same path, HALT on anything under `archive/` (that change has shipped, its delta is folded, and it is the only artifact the `Change:` trailer traces to), and **proceed** only when re-rendering *this* change live, replacing the directory's prior contents. `design.md` §2 and `tasks.md` still state the halt unconditionally; reconciling them is the human's, since it means editing the change.

- **A different root `CLAUDE.md`, and the security posture that follows** (change `0007-pm-side-process-standard`, phase 3). Running from the vault means the *vault's* operating manual is the loaded instruction set and the repo's is not, so each retargeted skill now **names the repo files it needs** rather than assuming repo context. The consequence is a quiet improvement rather than a cost: the target repo's `CLAUDE.md` becomes **data the skill reads**, not **instructions the harness obeys** — the posture `mf-teardown`'s untrusted-target clause argues for, now true by construction for the whole line. The framing travels with the delegations, stated inside the block a spawned subagent actually receives, since a fresh subagent inherits none of the parent's setup context. **One skill of four stays on the old model by design** (`design.md` §5): `mf-teardown` still reads `.env` → `VAULT_PROJECT_DIR`. ## [0.5.0] - 2026-08-24

**v0.5 — the change cutover.** v0.3 built, spec'd and unit-tested the in-tree change reader and then never wired it in: `driver.run` still defaulted to the vault-plan reader, the vault had since dropped `implementation_plans/` entirely, and the framework was **broken against its own vault** — a run died on an uncaught `ValueError` from `max()` over an empty glob instead of the diagnostic the preflight exists to produce. Two shipped specs asserted contradictory behaviour about where progress is read, and the one actually wired was the retired one. A pure, stdlib-only module (`ast`, `pathlib`, `tomllib` — no new dependency) that reads two sides of the scenario↔test binding from disk and compares them: the **spec side** parses scenario keys (`Key:` + `Layers:` bullets) from `specs/**/spec.md` (shipped) and each active `changes/*/specs/**/spec.md` delta (`changes/archive/` excluded; delta `ADDED`/`MODIFIED` keys are resolvable-but-pending, `REMOVED` subtracts), and the **test side** statically collects `@pytest.mark.spec(...)` / `@pytest.mark.spec_exempt(...)` markers with `ast` — the checker never imports or runs the tests or the gate. Wired as the final step of MF's own gate (`.minions/minions.toml`, `Makefile`, `.github/workflows/ci.yml`) — a green no-op until specs exist. `spec` / `spec_exempt` registered in `pyproject` `[tool.pytest.ini_options].markers`.

## [0.2.0] — 2026-08-21

### Added

- Preflight / contract guard (`orchestrator/state.py`) — the orchestrator's fail-closed read-side of the target contract, checked **before any spend**. `validate_plan(frontmatter)` refuses a malformed plan at read time (no `---` fence · missing `current_phase` · no `phaseN` flags · a non-code phase status outside `{done, wip, planned, todo}`) with a specific `PlanContractError` per violation — catching the *silent* failure where a zero-phase plan would read as already "complete", and the non-code-phase case the driver would otherwise false-halt on mid-run (the execution-side mirror of `/plan-check`; a non-code phase can't be told from a code phase structurally, so an out-of-vocabulary status *is* the signal). `read_plan_state` now validates before assembling. `verify_vault_access(repo, vault)` preflights that the target's `.claude/settings.local.json` grants the coder vault write access (the vault dir or an ancestor under `additionalDirectories`), raising `PreflightError` otherwise. `__main__` runs both as a zero-token preflight that prints a clean diagnostic and exits `1` before spawning anything.
- Release automation (`orchestrator/release.py`) — the run's last deterministic stage: verify the release gate, then prepare the release locally and **halt for the human to merge + push** (the boundary never crosses — prepare locally, the human ships). `verify_release_gate(...) -> ReleaseVerdict` is **pure** — the release-time analog of `driver.decide`, judging already-gathered facts (gate result · the three findings `clean` · backlog current-release section closed · release tag free · CHANGELOG `[Unreleased]` non-empty · clean tree) as one first-non-`None` scan over `str | None` blockers, so it is unit-tested with plain data (no fakes needed). The predicates **fail closed**: a malformed backlog (missing current-release section) or an empty/missing `[Unreleased]` blocks release rather than silently passing (absence of evidence ≠ evidence of absence). `prepare_release(...)` refuses on a red verdict — a true no-op, the repo left byte-for-byte untouched — else cuts the CHANGELOG (`[Unreleased]` → `[X.Y.0]`, re-seeding a fresh `[Unreleased]`), bumps `pyproject` (line-anchored regex — no TOML round-trip, no new dependency), commits + annotated-tags **locally**, prepends the vault `release_log.md`, and returns the merge+push handoff. The **"never push" boundary is structural**: the injected `ReleaseGit` seam (real `SubprocessReleaseGit` + recording `FakeReleaseGit`) has no `push`/`merge` method, so prepare *cannot* ship. Wired into `driver.run()` via a new injected `release` seam invoked after `converge()` at plan-complete — a converge halt returns before it, a refused release halts the run, a prepared release completes it. The shared `all_findings_clean` predicate moved to `findings.py` (used by both converge and release); `__main__._make_release` is the composition root that gathers the facts for the pure verify then prepares (dogfood-validated, like `_make_converge`).
- Converge loop (`orchestrator/converge.py`) — drives open **blocking** review findings to clean by looping *fix → gate → scoped re-verify*, or halts. Pure deterministic control flow, **no LLM in the loop**: it re-reads the three findings files from disk each round and gates convergence on `verdict == "clean"` for all three (the verifier-owned, un-gameable signal), discarding the fixer's return entirely. Terminates by construction — halts at `rounds ≥ max_rounds` (round cap) or a red gate after a fix. Built on injected seams (`read_states`, `run_verify`) so the whole state machine is unit-tested behind `FakeProvider` + `FakeGate`: the full matrix — already-clean (zero rounds), fix→verified (one round), reopen, round-cap halt, red-gate-after-fix — is green with no real roles. Wired into `driver.run()` via a `converge` seam invoked after `fanout()` at plan-complete (they communicate through the findings files on disk, not return values); a converge `HALTED` propagates to a run halt.
- End-of-plan fan-out (`orchestrator/fanout.py`) — `run_fanout(...)` runs the three read-only roles (review ‖ security ‖ simplify) over the frozen `base..HEAD` diff, composing P1–P3: for each role it builds `read_only_profile` (P2), injects the diff as a file via `run_role_with_diff` (P2), emits `role-spawn`/`role-returned` status events (P1), and collects the verdict via `read_findings_state` (P3). Sequential (a plain loop — parallel is a noted-not-built optimization) and data-driven (one loop over a `RoleSpec` table, not three near-identical functions). Wired into `driver.run()` via a new injected `fanout` seam invoked once at plan-complete (a halted build never fans out; a build-only run defaults to a no-op). Fully unit-tested behind a recording `FakeProvider` (three read-only spawns over the frozen diff, per-role events, verdicts collected); the first live run — including `simplify.md`'s first-ever execution — is the P4 dogfood (pending). `__main__` wires the real fan-out: a closure that computes the frozen diff at invoke-time (not bind-time, since the final `HEAD` doesn't exist until the build finishes), plus a `--base` arg, the three role prompts, and plan-version resolution.

### Added

- Role summaries surfaced on the status stream — `RoleReturned` now carries the role's final message (`summary`, filled from the parsed `RoleResult.result`), and `render` shows a trimmed gist under the returned line (`↳ …`; full text in `events.jsonl`). So when a role **halts intentionally** — a coder stop-condition such as *the plan contradicts reality* — you see **why** inline instead of a bare "phase did not advance". Surfaced by the first dogfood: the coder correctly halted on a real scheduling infeasibility (a weekly-rest constraint that made the example roster impossible) and asked for a decision, but the reason was being discarded.
- Graceful provider-error handling — `ClaudeCodeProvider.run_role` now raises a typed `ProviderError` on a non-zero `claude -p` exit (an API error or subscription usage limit) instead of letting `CalledProcessError` crash the run with a raw traceback. `driver.run()` catches it around the coder spawn and turns it into a clean, observable **halt** (emits a `halt` event + `run-summary`, returns `HALTED`), so the run stops **resumably** — re-running picks up from the last committed phase via disk state — and `__main__` backstops the same error in the fan-out/converge/release stages with a readable message + a distinct exit code. Documented behaviour surfaced by the first live dogfood, where a subscription usage limit crashed the run mid-phase.

So a run is reproducible on an explicit model + effort instead of an implicit machine default.

### Changed

- Reverted the coder to the **per-phase** model (the warm whole-plan coder was a wrong turn the first dogfood exposed): `coder.md` now builds **exactly one phase per spawn** then STOPs, and the driver's existing per-phase loop gates + detects advance + re-spawns per phase. This restores per-phase un-gameable gating, **per-phase CLI/log visibility** (each phase emits `phase-start` → `gate ✓` → `advanced`), and **crash resilience** (a failure loses only the current phase; committed phases are safe) — the three gaps that appeared when a subscription limit crashed a warm 6-phase session mid-P3. `coder.md` also gains **resume-mid-phase detection**: on a `git status` showing uncommitted work it recognises an interrupted phase, continues it (rather than restarting), and logs that it resumed.

- Gate config relocated to `.minions/minions.toml` (`gate.py` `read_gate_commands`, was `repo/minions.toml`) — consolidating the committed gate config with the generated `.minions/` run artifacts (one framework dir per target, behind a selective ignore `.minions/*` + `!.minions/minions.toml` in the target). A missing config now raises a clear `FileNotFoundError` ("the target must ship .minions/minions.toml") instead of a bare traceback deep in a run. `tests/test_gate.py`, `README.md`, and `docs/modules/gate.md` updated to match.
- Unified the coder-specific `CoderSpawn`/`CoderResult` status events into generic `RoleSpawn`/`RoleReturned` (carrying a `role: Role` — `Literal["coder","review","security","simplify"]`, one alias reused by `fanout.RoleSpec.name`), so the fan-out roles reuse the same spawn/returned events instead of a parallel pair. The coder is now `role="coder"`. A missing file returns `None` (a not-yet-run role, not a crash), keeping `verdict` strict and forcing callers to handle "not run". This is the orchestrator's un-gameable convergence signal — owned by the verify pass, read from disk, never trusted from the fixer's word.
